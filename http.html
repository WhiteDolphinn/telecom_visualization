Настройки сети, скорость и ручные потери

Кнопки сценариев начинают весь запуск заново с нулевого времени. Кнопки перехода меняют момент на той же общей шкале, сохраняя трассы. Случайные и ручные потери доступны здесь для свободного исследования.

RTT — время пути туда и обратно. Канал задаёт общую скорость передачи всех соединений в одном опыте. Seed задаёт воспроизводимый набор случайных потерь.

Ручная потеря изменяет только выбранный протокол: из-за разного времени старта один и тот же блок в другом опыте может уже прийти. Выбор пакета останавливает время. Можно нажать и на пакет в анимации; при наложении откроется выбор. 1× = 120 мс модели в секунду. Жёлтая метка у сервера — сериализация. Seed: 42.

«Повторить» сохраняет ручные потери. После возврата назад новая ручная потеря отменяет будущие ручные потери в выбранной трассе. Изменение параметров сети, сценария или seed начинает новый опыт без ручных потерь.

Один момент времени — три протокола рядом

Зачем HTTP/2 одно TCP-соединение? В HTTP/1.1 без pipelining два TCP позволяют получать два ответа параллельно; остальные запросы ждут полного предыдущего ответа в своём соединении. HTTP/2 может запросить все четыре объекта и чередовать части их ответов в одном TCP.

Сравните число объектов с данными и очередь запросов. Преимущество HTTP/2 — много запросов на одном соединении. Общая скорость канала остаётся прежней; время всей загрузки зависит от условий.

Чем приходится платить за дополнительные TCP?

Установка и ресурсы. Для каждого нового защищённого TCP нужны свои TCP/TLS-рукопожатия, буферы и состояние на клиенте и сервере. Два соединения можно устанавливать параллельно: задержка не обязана удваиваться, но работы и служебного трафика больше. HTTP/2 позволяет обслуживать много запросов с одним набором этих затрат.

Масштабирование. Два TCP облегчают очередь HTTP/1.1, но при десятках объектов очередь остаётся. Дальнейшее увеличение числа соединений расходует дополнительные ресурсы и создаёт больше независимо конкурирующих отправителей. Потоки HTTP/2 используют одно TCP и его общее окно.

Обратная сторона одного TCP. В HTTP/1.1 потеря данных одного соединения не блокирует выдачу из другого. В HTTP/2 пропуск в TCP задерживает выдачу всех его потоков. HTTP/3 переносит порядок доставки на уровень отдельных потоков QUIC; общий канал и управление перегрузкой по-прежнему связывают их скорости.

В этой демонстрации видны очередь запросов, число соединений, этапы установки и эффект потерь. Расход памяти, процессорное время, объём служебного трафика и сжатие заголовков не рассчитываются. Поэтому секундомер не показывает всю цену дополнительных TCP. Основание: зачем создан HTTP/2 и издержки параллельных соединений.

Как читать единый запуск и какие допущения сделаны?

Время 0 — отправка SYN у HTTP/1.1 и HTTP/2 и QUIC Initial с ClientHello у HTTP/3. Сначала устанавливается защищённое соединение, затем HTTP-запрос достигает сервера, и только после этого начинается отправка блоков ответа. Все три колонки показывают один и тот же момент, шкалы времени одинаковы.

Для нового HTTPS-соединения выбран TLS 1.3: TCP + TLS позволяют отправить запрос через 2 RTT; QUIC + TLS — через 1 RTT. Третий ACK TCP может уйти вместе с ClientHello. Все TCP HTTP/1.1 устанавливаются параллельно; их задержки не складываются. Режим «Уже установлено» сохраняет готовые защищённые соединения: это повторное использование, а не 0-RTT нового соединения.

Все объекты уже известны клиенту и доступны серверу. DNS, размеры служебных сообщений, потери рукопожатия, TCP Fast Open, QUIC Retry, TLS HelloRetryRequest, ограничения anti-amplification, обработка сервера и HPACK/QPACK не моделируются. В учебном режиме HTTP/1.1 допускается не более 2 TCP-соединений, как на слайде 13 презентации. В каждом соединении отключён pipelining. Это ограничение модели курса, не универсальный предел современного HTTP/1.1. Один общий канал задан отдельно для каждого сравниваемого опыта, а не одновременно делится между тремя протоколами. Стартовое окно каждого соединения — 8 блоков. Поэтому несколько TCP HTTP/1.1 могут получить большую суммарную квоту; фиксированного победителя нет.

TCP сохраняет один порядок байтов на соединение. HTTP/2 чередует ответы потоков в одном TCP. QUIC сохраняет порядок отдельно в каждом потоке; потери могут уменьшать общее окно и задерживать будущую отправку. «Первый блок» — полностью полученный и выданный приложению блок из 1200 байт, а не первый байт страницы. Цветная полоска показывает прошедшую часть каждой стадии.

Источники и модель передачи данных

Для каждого протокола время прибытия первого HTTP-запроса ограничивает начало ответа. В HTTP/1.1 следующие запросы внутри TCP отправляются после полного предыдущего ответа. Все соединения одного опыта делят один сериализатор канала; ни рукопожатия, ни окна нескольких TCP не умножают заданную пропускную способность данных.

Потери определяются номером блока, попыткой и seed. HTTP/2 и HTTP/3 при одинаковых потерях имеют одинаковое расписание данных относительно начала ответа, но разное абсолютное начало и разный порядок выдачи приложению. Ручные потери независимы. ACK данных приходит через RTT после сериализации; потеря обнаруживается через 1,5 RTT. Это учебный планировщик, а не реализация recovery.

Объекты имеют размеры 3, 7, 9, 11, 13, 15 блоков по 1200 байт; «видео» — небольшой учебный фрагмент. График включает выбранный режим установления соединения, использует 60 seeds на точку и исключает плановые/ручные потери. Интервалы — приближённые 95% интервалы среднего.
